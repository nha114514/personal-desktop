# 主模型与子代理控制：执行交接

请在 `D:\desktop\personal-desktop` 的现有 Personal Desktop 项目中实现以下需求。当前分支为 `personal-desktop`，已有大量未提交修改。先检查现状，保留所有已有工作，不执行 reset、clean、回退或整批覆盖。遵循仓库 AGENTS.md、需求记忆预检和现有 Cordis、配置、工具授权、前端插槽及测试风格。

## 用户明确要求

1. 核心思考、总体计划、架构选择、重要决策、任务分配和最终验收由用户选择的主模型负责。子代理提供执行结果，主模型负责判断和汇总。不得把主控职责整体转交给某个“主要子代理”。
2. 主模型和推理等级读取用户的实际选择，不能硬编码模型名称，不能由 Agent 自行更换。主模型发生鉴权、额度或模型不可用错误时，明确报错；不得偷偷用其他模型继续主控流程。
3. 只允许主代理创建子代理，且只能使用用户在界面明确授权的精确 provider/model 路由。默认路由、继承、显式参数、恢复任务及备用模型都必须遵守授权。安装或注册了一个模型不等于用户授权了它。
4. 子代理是执行叶节点，不能再创建子代理，也不能委派给现存代理来间接产生下一层。禁止“主代理 → 子代理 → 子代理”的递归，最多只有主代理这一层委派。原有最多 8 个子代理并行的容量可以保留。
5. 子代理可继续使用写代码、调试、检索及 Skill 等必要执行工具；Skill 不能重新启用被禁用的代理工具。子代理的推理等级遵守用户选择及对应模型的实际支持能力。

## 必须实施的技术控制

- 先列出所有实际委派入口和调用路径，包括进程内 subagent、外部 Codex/MiMo/ACP 委派、团队工具、发送/续行工具，以及 Skill 能调用的入口。以实际代码为准，不假设当前已有配置就能覆盖所有路径。
- 复用现有运行身份、父子关系、工具 ACL 和模型授权机制。主控角色绑定用户选择的主模型；执行角色只能获得被授权的子代理路由和非委派工具。客户端选择用于配置，后端执行前负责校验。
- 子代理工具目录不公布创建、恢复或间接委派代理的能力。服务端创建及续行入口同时拒绝子代理的委派请求，防止绕过 UI、遗漏工具或直接调用。仅写系统提示词或只把 maxDepth 改成 1 不算完成。
- 未指定模型时，也要校验解析后的最终路由。关闭“允许 Agent 选择模型”时，只能使用用户配置的子代理默认路由；开启时只能在用户授权集合中选择。默认模型配置与授权不一致时明确报告，不得继承到未授权模型或扩大名单。
- 限制必须覆盖会话恢复、配置变化、后台任务和外部 CLI。对于外部 CLI 自带的代理能力，查证其实际配置或权限控制；不能保证禁止继续派生时，明确限制该执行方式，不得宣称已强制禁止。说明任意 shell/代码执行与外部系统的实际控制范围，不把提示词描述成安全沙箱。
- 界面明确显示主模型/推理等级、子代理默认模型/等级及授权集合，说明子代理不能继续派生。现有“任意 API 模型添加”能力需要保留，新增提供方不自动加入授权集合。显示的实际运行模型应能与会话日志对应。
